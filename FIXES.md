## F1 (P0) Change the promise wording

**Problem.** The Locked section says "every household served exactly once, even with no comms". In Safe mode some
households wait until comms return, so "exactly once, even with no comms" is false, and Neptune North's engineers
will spot it. "Exactly once" is also a known red-flag phrase in distributed systems.

**Proposal.** Promise: **"Never served twice. Everyone served eventually."**
- Safe mode guarantees *never twice*. *Eventually* holds once vans can talk again (or in Lifeline mode, sooner).
- When talking about messages, say "messages may arrive twice but merge safely", never "exactly-once delivery".

**Check.** `PLAN.md` Locked, README, pitch and Devpost text all use the new wording.

## F2 (P0) Safe-mode ownership uses the fixed starting roster

**Problem.** `PLAN.md` "How it works" #1 computes `owner(h)` over "the vans that van currently believes are alive".
Two vans with different alive-lists then compute different owners for the same household, so a double serve becomes
possible **even in Safe mode**, which breaks our main guarantee.

**Proposal.**
- `ROSTER` = the list of van ids at tick 0. It never changes.
- **Safe mode:** `hashOwner(h) = argmax over v in ROSTER of hash(h.id, v.id)`.
- **Lifeline mode:** `hashOwner(h) = argmax over v in aliveView of hash(h.id, v.id)`, where `aliveView` is this van's
  own view (see F10 for what that costs).
- The hash must be a deterministic string hash (e.g. FNV-1a over `h.id + '|' + v.id`), never `Math.random`.

**Check.** Unit test: two vans with different alive-lists compute the same Safe-mode owner for every household.

## F3 (P0) Specify the handover protocol

**Problem.** "How it works" #4 says vans "hand households to whichever is closer", but the hash rule alone can't
represent a handover, and a handover over a lossy radio can leave both vans thinking they own the household
(double serve) or neither. This is the two-generals problem and the judges may ask about it.

**Proposal.**
- Each van keeps `overrides: Map<householdId, {owner, version}>`. Effective owner:
  `owner(h) = overrides.has(h) ? overrides.get(h).owner : hashOwner(h)`.
- **Merge rule (gossip):** for each household keep the entry with the higher `version`; on a tie, the higher `owner` id
  wins. This is a CRDT (last-writer-wins by version), so messages arriving twice or out of order merge safely.
- **Only the current owner (in its own view) may create a new version** for a household.
- **The giver lets go first:** van A hands `h` to B by setting `overrides[h] = {owner: B, version: v + 1}` locally
  *before* sending the offer. From that moment A no longer owns `h`. B adopts it when the offer (or later gossip from
  A, which carries the same entry) arrives.
  - Lost offer: `h` is briefly unowned. It is never double-served. B learns of it at the next gossip with A, or Lifeline
    picks it up after the timeout.
  - Pitch line: *"When a handover message is lost, we lose speed, never correctness."*
- **Stock** is passed only when two vans are physically together (distance ≤ 1 cell). It is a physical hand-off,
  modelled as reliable, and is separate from the radio.
- A van serves `h` only if `owner(h) === self` in its own view **and** `h` is not in its `served` set.

**Safety invariant (for F9's checker).** In Safe mode, at every tick, for every household, at most one van's view says
`owner(h) === self`. The observer can check this from the van states without feeding anything back.

**Check.** Bench with high packet loss: the invariant holds in every Safe-mode run.

## F4 (P0) Run Web Workers in lockstep

**Problem.** Workers reply in whatever order they finish, so the order of actions changes from run to run, and the
"seeded and replayable" claim silently breaks in the live view.

**Proposal.** Each tick the main loop:
1. sends every van its percept (including that tick's `radio.deliver(t)` inbox),
2. waits for **all** vans to reply (`Promise.all`),
3. applies the actions **in van-id order**, then puts outboxes into `radio.send`.

The headless bench calls `stepVan` directly in the same order, so live and bench give identical results for a seed.

**Check.** Same seed, same jam actions: the live view and bench produce identical metrics.

## F5 (P0) HQ contract: send real audio, not a file path

**Problem.** The contract sends `"audio": "samples/sos_h17_ar.mp3"`. n8n is a separate process and cannot open a path on
the sim's machine. Also, `cd sim && python -m http.server` serves only `sim/`, so `hq/samples/` isn't reachable at all.
The reply's `audio_url` has the same problem: n8n would have to host the file somewhere.

**Proposal.**
- Put SOS clips in `sim/samples/` (served by the sim's web server).
- Request: `audio` becomes an absolute URL, e.g. `http://localhost:8000/samples/sos_h17_ar.mp3`. n8n fetches it with
  an HTTP Request node (works if n8n runs on the same laptop, see F8).
- Response: replace `audio_url` with `audio_b64` (base64 MP3) plus `mime: "audio/mpeg"`. The sim plays it with
  `new Audio('data:audio/mpeg;base64,' + audio_b64)`. No file hosting needed.
- Keep `text` in the response so the UI can show a caption even if audio fails.

**Check.** `contracts/sos_batch.example.json` updated. A curl call with the example request returns playable audio.

## F7 (P0) De-duplicate SOS across n8n runs

**Problem.** The same SOS can be carried by two vans and arrive in two different batches, minutes apart. Each batch is a
separate n8n execution, so de-duplicating inside one execution is not enough.

**Proposal.** Before processing, look up `sos_id` in the Google Sheet log (or use n8n's Remove Duplicates node if your
version supports removing items seen in previous executions). Already seen: return the stored reply, don't reprocess.
This matches the sim's promise: one need, handled once.

**Check.** POST the same batch twice: one Sheet row, same reply both times.

## F9 (P1) Safety invariant check, 1,000 seeds, replay-seed button

**Proposal.**

## F10 (P1) Lifeline mode: document and count every source of double serves

**Problem.** In Lifeline mode, live vans with different alive-lists can also disagree with each other (not only with the
silent van), so double serves come from two sources. And when a silent van comes back, its households move back.

**Proposal.** Write both sources down in `PLAN.md`, count them separately in metrics, and show the total. When a dropped
van is heard from again, it rejoins `aliveView`. Households already in the merged `served` set are skipped, so rejoining
causes no new double serves.

## F11 (P1) Say clearly how a household's SOS is recorded

**Problem.** Judges will ask: "If phones are down, how does a household send a voice SOS?"

**Proposal.** The household records the SOS on the van's device **when the van serves it** (for needs on the next run,
e.g. "my mother needs insulin"). In code this is already natural: a van picks up `sos` only from a household it is
serving (`pickupSos` in the same tick as `serve`). Use this exact sentence in the pitch and on Devpost.

## F14 (P2) Door tags: households carry notes between vans

**Idea.** After Hurricane Katrina, rescue teams spray-painted X-codes on doors to record who had searched a house and when.
We make that digital: each household has a tag. A van serving or passing a household writes a small note to it
(`{servedBy, t, overridesSnapshot, sosPending}`); the next van that passes reads it. Information then spreads through
places, not just the radio, so it still flows under total jamming. Swarm-robotics research calls this stigmergy.

**Interface change.** `world.js`: `household.tag = []` (small, capped list). Percept: `seenHouseholds[i].tag`.
Action: `writeTag: {householdId, note} | null`. Tags merge with the same CRDT rules as gossip (F3), so they can't break
the safety invariant.

**Demo moment.** Jam the whole map, then show a van learning about a handover or an insulin need from a door.
Pitch line: *"When the radio dies, the street becomes the network."*
